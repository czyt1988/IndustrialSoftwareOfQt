# 电子设计：两种界面框架的分岔

!!! abstract "本章要点"
    EDA 的核心是两张互相映射的网：原理图的连接关系，和 PCB 的物理实现。KiCad 与 LibrePCB 代表了两条不同的工程路线：一个用 wxWidgets 熬了三十年，把工具框架做到极致；一个用 Qt 和现代 C++ 重写，把类型安全和事务做到极致。读它们，比读十篇“Qt 最佳实践”有用。

## 4.1 两张网

电子设计自动化的数据模型，本质上是两张网。

**第一张是逻辑网。** 原理图里有符号、引脚、连线、网络标签。用户画的是“这个电阻的一端接到 MCU 的 PA1”，而不是“这条线在坐标 (120, 340) 到 (180, 340)”。网络（net）是逻辑实体，符号只是它的可视化形式。

**第二张是物理网。** PCB 上有封装、焊盘、走线、过孔、铜层。同样的网络在这里变成具体的铜箔路径，还要满足线宽、间距、阻抗、层叠的约束。

两张网通过“封装映射”连起来：原理图里的 `R1` 对应 PCB 里的一个 0603 封装，引脚 1 对应焊盘 1。改原理图要同步到 PCB（前标注），改 PCB 的封装要反推回原理图（后标注）。这个双向同步如果做错，板子做出来就是废的。

EDA 软件的复杂度主要来自三处：

- **连通性计算**：几万个网络、几十万个连接，要实时判断“这条线能不能走”。
- **设计规则检查（DRC）**：间距、线宽、孔径、阻焊、丝印，规则越多，检查越慢。
- **交互密度**：一块板上有上万个可点击对象，选中、高亮、过滤必须精确。

这三件事和界面框架关系不大，但和“界面怎么组织交互”关系极大。

## 4.2 KiCad 为什么不用 Qt

KiCad 是这个领域最重要的开源项目，而它用的是 wxWidgets。这件事经常让 Qt 开发者困惑。

原因不复杂。KiCad 1992 年起步，那时 Qt 还没有今天的地位，wxWidgets 已经是跨平台原生控件的成熟选择，而且许可证对 GPL 项目没有障碍。三十年后，重写界面的成本远高于忍受 wxWidgets 的缺点，于是它就一直用下来了。

代价是真实存在的：wxWidgets 的控件能力有限，KiCad 大量使用自绘；高 DPI 支持比 Qt 晚了好几年；不同平台的观感不完全一致。但收益也真实：安装包小、启动快、原生控件的行为符合各平台习惯、许可问题简单。

这件事的启示不是“wxWidgets 比 Qt 好”，而是：**界面框架的选择往往由历史决定，而不是由技术优劣决定。** 一个能活三十年的软件，靠的是数据模型和工具链的稳定，不是界面框架的先进。

还有一个细节值得注意：KiCad 的三维查看器并不自己写几何内核，STEP 模型的读入靠的是 OpenCASCADE。界面用 wxWidgets，内核用 OCCT，两者互不干涉。这正好印证了第 1 章的判断：界面可以换，内核不能省。

## 4.3 KiCad 的工具框架

如果只从 KiCad 抄一样东西，抄它的工具框架。

EDA 的交互有个特点：大量操作是“多步、可中断、可回退”的。布线要点击起点、移动、换层、打孔、再点击终点；测量要先选起点再选终点；框选要判断修饰键。如果用传统的“事件处理函数 + 状态变量”来写，代码很快会变成一锅粥。

KiCad 的做法是把每种交互抽象成一个“工具”（tool）：

- `TOOL_MANAGER` 负责注册、调度、切换工具。
- 工具通过协程（coroutine）实现“等待下一个事件”，代码可以写成顺序逻辑，而不是回调嵌套。
- 工具产生的修改通过“提交”（commit）对象统一进入撤销栈。

这套设计的效果是：布线器和选择工具在代码结构上是同一种东西，多步交互写起来像同步代码，撤销的粒度由提交控制。

```cpp
// 结构示意，非 KiCad 源码
class RouteTool : public ToolBase {
public:
    int MainLoop() override {
        while (auto evt = WaitForEvent()) {     // 协程挂起，等待用户输入
            if (evt->IsClick())   addCorner(evt->Position());
            if (evt->IsKey('V'))  toggleLayer();
            if (evt->IsCancel())  { rollback(); return 0; }
        }
        return 0;
    }
};
```

这是把“命令模式”从数据层扩展到控制层的典型做法。Qt 本身没有协程，但 C++20 的 coroutine 或者简单的状态机都能实现同样的效果。第 9 章会给出一个可用的最小实现。

## 4.4 LibrePCB：现代 C++ 的另一种答案

LibrePCB 是新一代的 EDA 项目，Qt + GPLv3，代码量比 KiCad 小一个数量级，但工程质量很高。

它最值得学的是**类型安全**。长度、面积、角度、电压，这些量在 C++ 里默认都是 `double`，混用是 bug 的温床。LibrePCB 用强类型把它们区分开：`Length`、`PositiveLength`、`UnsignedLength` 是不同类型，编译期就能拦住“把负长度传给焊盘”这类错误。

第二个是**事务式撤销**。一次编辑被包成一个事务，事务内的所有修改要么全部生效，要么全部丢弃。对于“移动器件 + 自动重连 + 更新网络”这种复合操作，事务比一条条命令更符合语义。

第三个是**库的管理**。LibrePCB 把元件库当成项目的一部分来管理，有明确的版本、依赖和更新机制，而不是像早期 KiCad 那样依赖全局库路径。这个问题在团队协作里非常要命。

## 4.5 两条路线的对照

| 维度 | KiCad | LibrePCB |
| --- | --- | --- |
| 界面框架 | wxWidgets | Qt |
| 规模 | 百万行级，三十年积累 | 十万行级，十年积累 |
| 优势 | 功能完整、生态成熟、格式稳定 | 类型安全、事务清晰、易读易改 |
| 代价 | 历史包袱重、自绘多、上手慢 | 功能覆盖少、生态小 |
| 适合抄什么 | 工具框架、连通性算法、文件格式 | 领域建模、撤销事务、库管理 |

两者都是 GPLv3。如果你的产品要闭源，这两个项目只能“参考思想”，不能链接代码。这一点在第 10 章的许可证部分会展开。

## 4.6 启示

EDA 给工业软件开发者上了三课。

**第一课，领域模型的类型安全值得投入。** 一个 `double` 到处传的代码库，三年后没人敢改。把单位、正负、量纲做成类型，前期多写几百行，后期省下几百个 bug。

**第二课，多步交互需要专门的抽象。** 不要用状态机硬堆，也不要指望 Qt 的事件系统自动帮你解决。工具 + 协程 + 提交，是被验证过的组合。

**第三课，界面框架的选择没那么重要。** KiCad 用 wxWidgets 也能做到世界第一梯队的开源 EDA。真正决定成败的，是连通性算法、文件格式的兼容性，以及三十年不间断的维护。
