# 科学可视化：场景图与管线

!!! abstract "本章要点"
    科学可视化软件几乎都建立在同一个母题上：数据源经过一串过滤器，最后交给渲染器。差异只在于管线是显式的（VTK、ParaView、VisIt）还是隐式的（Slicer 的场景图、Inviwo 的处理器网络）。理解这个母题，你就能在半小时内看懂一个陌生的可视化项目。

## 6.1 一条管线，三种数据

无论界面长什么样，可视化系统的内部都可以画成一条线：

> 数据源（source）→ 过滤器（filter）→ 映射器（mapper）→ 渲染器（renderer）

数据源负责读文件或生成数据；过滤器做切片、等值面、流线、抽稀；映射器把数据转成图元；渲染器负责画。

管线的价值在于**按需计算**。用户拖动时间轴，只有受影响的过滤器需要重新执行；视角变化不影响数据，只触发重绘。VTK 把这套机制叫 demand-driven pipeline，每个 `vtkAlgorithm` 只有在被请求时才 `Update()`。

数据对象则只有三大类：

- **结构化网格**（image data / structured grid）：数组下标隐含坐标，适合图像和规则网格。
- **非结构化网格**（unstructured grid）：显式存单元和连接，适合有限元。
- **多边形数据**（poly data）：点、线、面，适合曲面和等值面。

外加标量、矢量、张量这些“属性数组”挂在点上或单元上。几乎所有后处理软件的“云图”，都是属性数组经过颜色映射的结果。

## 6.2 VTK：这个领域的操作系统

VTK 是科学可视化的基础设施，BSD-3 许可，三十多年历史。ParaView、Slicer、VisIt、Mayo 的渲染层，甚至很多商业软件，都直接或间接用它。

VTK 的强项是覆盖面：几十种文件格式、上百个过滤器、多种渲染后端（OpenGL、WebGL、OSPRay）。弱项是 API 风格老派、编译体积大、学习曲线陡。

把 VTK 接进 Qt 是每个做可视化的人都要过的一关。VTK 9 之后提供了 `QVTKOpenGLNativeWidget`，把 `vtkRenderWindow` 嵌进 `QWidget`，同时处理高 DPI、上下文共享和事件转发。要注意的是，VTK 有自己的交互器（interactor），和 Qt 的事件系统会打架，通常的做法是关掉 VTK 的交互器，把鼠标事件翻译成相机操作。

## 6.3 ITK：图像处理的另一半

ITK 和 VTK 经常一起出现，但分工明确：VTK 管“看得见”，ITK 管“算得出”。

ITK 的核心是图像和过滤器。`itk::Image` 支持任意维度和像素类型，过滤器覆盖配准、分割、形态学、滤波。它的管线也是按需更新，还支持流式处理：把大图像切成块，逐块读入、逐块处理，内存占用可控。

ITK 不做界面，也没有渲染。它是纯算法库，通常被包在一个 Qt 应用里，前面接 DICOM 读取，后面接 VTK 显示。

## 6.4 CTK：把“插件”做成基础设施

CTK（Common Toolkit）是一个常被低估的项目。它提供三样东西：类 OSGi 的插件框架、DICOM 数据库与网络、一组 Qt 控件。

它的插件框架值得单独说。插件有生命周期（安装、启动、停止、卸载），有服务注册表，插件之间通过接口查找而不是直接依赖。这套东西在 Java 世界里很常见，在 C++/Qt 里少见，但对大型工业软件非常合适：几十个团队各写各的模块，运行时才组装。

Slicer 就是这套框架的重度使用者。

## 6.5 3D Slicer：场景图驱动的典范

Slicer 是医学影像领域的开源旗舰，Qt + VTK + ITK，BSD 风格许可。

它的核心抽象是 **MRML 场景**：一个 `vtkMRMLScene` 持有所有节点（图像、模型、变换、标注、相机），节点之间可以引用。界面上的每一个面板、每一个视图，都是场景的观察者。改场景，所有视图自动更新；撤销，场景回滚。

模块分三类：

- **CLI 模块**：一个可执行程序加一个 XML 描述，Slicer 负责生成界面、调用、收集结果。这是最轻的扩展方式。
- **Loadable 模块**：C++ 编译的 Qt 插件，能深度定制交互。
- **Scripted 模块**：Python 写的模块，能力接近 Loadable，开发快得多。

这个“三档扩展”设计非常值得抄：轻需求用 CLI，中需求用 Python，重需求用 C++。用户不必一上来就写 C++ 插件。

## 6.6 Inviwo：把管线变成画布

Inviwo 是可视化研究领域的快速原型工具，Qt + OpenGL，BSD-2。

它把可视化管线做成了可视化的网络：每个处理器（processor）是一个节点，端口（port）连数据，属性（property）暴露参数。用户在画布上拖节点、连线，就能搭出一条渲染管线，调参数实时看效果。

这种“数据流编程”的界面，对研究者极其友好，因为它把“改代码、重编译、看结果”的循环压缩成了拖拽。代价是性能优化空间有限，也不适合做最终产品。

Inviwo 的代码结构提醒我们：**如果管线是显式的，界面就可以是通用的。** 同一套节点编辑器，换一批处理器，就能变成另一个领域的工具。

## 6.7 VisIt：为超算而生

VisIt 是劳伦斯利弗莫尔实验室的作品，BSD-3，面向大规模并行数据的可视化。

它的架构从一开始就假设数据不在本机：客户端负责界面，服务端跑在超算上，中间传的是渲染结果或抽稀后的几何。它支持上百种文件格式、几十种绘图类型，扩展方式是插件（数据库插件、操作符插件、绘图插件）。

VisIt 和 ParaView 是同类产品，路线不同：ParaView 更通用、社区更大；VisIt 更偏向 HPC 工作流和批处理。读它们的架构对比，比读任何“架构设计”的书都直观。

## 6.8 这个领域的母题

把六个项目放在一起看，会看到同一个母题的不同变体。

| 项目 | 管线形态 | 扩展方式 | 适合学什么 |
| --- | --- | --- | --- |
| VTK | 显式过滤器管线 | C++ 子类 | 数据模型与渲染抽象 |
| ParaView | 显式管线 + 客户端/服务端 | 插件 + Python | 大型应用的插件化 |
| ITK | 显式过滤器管线 | C++ 模板 | 图像算法的工程化 |
| CTK | 服务与插件 | OSGi 式插件 | 模块解耦 |
| 3D Slicer | 场景图 + 模块 | CLI / C++ / Python 三档 | 场景驱动架构 |
| Inviwo | 数据流网络 | 处理器 | 可视化编程界面 |
| VisIt | 显式管线 + 并行 | 三类插件 | HPC 架构 |

如果只能记住一句话：**把数据和显示分开，把计算和交互分开。** 前者让你能换渲染器，后者让你能换界面。工业软件的寿命，往往就取决于这两条缝留得够不够宽。
