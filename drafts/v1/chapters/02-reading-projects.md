# 解剖一个工业软件项目

!!! abstract "本章要点"
    读一个大型工业软件，不要从功能出发，要从边界出发。目录结构暴露模块边界，文档类暴露数据模型，撤销栈暴露交互契约，插件注册暴露扩展点，构建脚本暴露依赖与许可。这五个剖面看完，你就能判断一个项目值不值得抄、能抄哪一部分。

## 2.1 先看目录，再看代码

打开一个陌生仓库，第一眼应该看顶层目录。工业软件的目录结构几乎从不撒谎，因为它是被构建系统强制的。

典型的形状是这样：

```text
src/
  core/        领域模型与算法，不依赖界面
  gui/         界面与交互，依赖 core
  app/         组装、启动、设置
  plugins/     扩展模块
tests/
cmake/
```

判断只需要一个问题：**`core` 能不能在没有 `gui` 的情况下编译？** 能，说明作者认真做过分层；不能，说明界面和数据模型缠在一起，这个项目大概率没法二次开发。

真实项目会给出更细的答案。

- **FreeCAD** 把 `App`（文档、对象、属性、算法）和 `Gui`（视图、命令、视口）做成两个库，`src/Mod` 下每个工作台又是一个独立模块。这条边界是它能在十几年里持续扩张的原因。
- **QGIS** 分成 `core`、`gui`、`app`、`plugins`，`core` 负责图层、坐标、渲染接口，`gui` 负责对话框和地图画布。PyQGIS 之所以好用，正是因为 `core` 不依赖界面。
- **3D Slicer** 分成 `Base`、`Libs`、`Modules`，每个模块声明自己依赖哪些库，模块之间通过 MRML 场景通信，而不是互相调用。
- **KiCad** 分成 `common`、`eeschema`、`pcbnew` 等，各工具共享 `common` 里的文档与工具框架，但彼此独立启动。

这条规律值得记住：**模块边界清晰的工业软件，扩展成本低；边界模糊的，功能越多越难改。**

## 2.2 文档模型：一切的根

每个工业软件都有一个“根对象”。找到它，就看懂了半个项目。

根对象的形态各不相同，但职责一致：持有数据、标识对象、管理生命周期、负责序列化。

| 项目 | 根对象 | 对象表示 | 序列化 |
| --- | --- | --- | --- |
| FreeCAD | `App::Document` | `DocumentObject` + `Property` | ZIP 包内的 XML（`.FCStd`） |
| 3D Slicer | `vtkMRMLScene` | MRML 节点 | MRB / MRML XML |
| QGIS | `QgsProject` | 图层、样式、关系 | `.qgs` / `.qgz` |
| LibrePCB | `Project` | 强类型实体 + 事务 | 目录结构 + 独立文件 |
| KiCad | `BOARD` / `SCHEMATIC` | C++ 类 + 字符串键 | S-表达式 |

观察根对象时，问三个问题。

**对象有身份吗？** 有没有稳定的 UUID 或者持久 ID。没有的话，复制粘贴、跨文档引用、增量保存都会出问题。

**对象之间有依赖吗？** 一个倒角依赖两条边，两条边依赖一个面，面依赖一个实体。依赖关系如果只是隐式的指针，改一个参数就要全量重算；如果显式建成图，就能做增量重算和失效传播。FreeCAD 的 `DocumentObject::execute()` 与属性依赖，本质上就是这张图。

**对象怎么存？** 序列化格式决定了文件能不能被别的工具读。XML 好调试，S-表达式紧凑且易 diff，二进制快但难兼容。选择本身不重要，重要的是有没有版本号和向前兼容策略。

## 2.3 命令层：撤销是信任的来源

用户敢在工业软件里大胆操作，是因为知道按 `Ctrl+Z` 能回来。撤销栈不是锦上添花，它是交互契约。

Qt 提供了 `QUndoStack` 和 `QUndoCommand`，但真正难的不是这两个类，而是**让所有修改都经过命令**。只要有一条路径直接改了模型，撤销栈就失去了完整性，用户迟早会踩到“撤销之后模型坏了”的坑。

看一个项目时，检查这几件事：

- 属性面板改一个数值，走的是命令还是直接写属性？
- 拖拽、旋转、批量删除，有没有各自的命令，还是合并成一条大命令？
- 命令能不能合并（连续微调滑块只产生一条撤销记录）？
- 撤销栈有没有和文档的“脏”标记联动？

KiCad 的做法更进一步。它把交互本身抽象成“工具”（tool），由 `TOOL_MANAGER` 统一调度，工具可以暂停、恢复、嵌套，配合协程处理“点一下、等下一个点”这种多步交互。这是把命令模式从“改数据”扩展到“控制流程”。

LibrePCB 则把修改包成事务：一次编辑要么整体生效，要么整体回滚，撤销栈里存的是事务而不是零散操作。对于“移动一个器件并自动重连网络”这种复合动作，事务比命令更自然。

## 2.4 扩展层：插件、脚本与文件

工业软件活不久的一个常见原因是扩展点没设计好。客户要一个特殊算法，你只能改主程序，改一次分叉一次。

成熟项目的扩展点通常有三层。

**二进制插件。** 通过稳定的 C++ 接口加 `QPluginLoader` 动态加载。难点不在加载，而在接口的二进制兼容：一旦发布，接口的虚函数表就不能随便动。Qt 自己的插件机制用 `Q_DECLARE_INTERFACE` 和版本号来约束这一点。

**脚本。** Python 是工业软件的通用语。FreeCAD、Slicer、ParaView、QGIS 都提供 Python 绑定，而且不是“只读 API”，脚本可以创建对象、执行命令、注册界面。代价是要维护绑定层，PySide/Shiboken 生成的绑定会随 Qt 版本漂移。

**文件与字典。** 最轻的扩展方式。Gmsh 用 `.geo` 脚本描述几何和网格，OpenFOAM 用字典文件描述求解设置，QCAD 用 ECMAScript 写绘图命令。文件即接口，不需要编译，也不需要 ABI 兼容。

评估扩展层时，看脚本能碰到多深：只能读结果，还是能改模型？能改模型，才谈得上二次开发。

## 2.5 构建：依赖的重量

工业软件的构建复杂度远超普通桌面应用，因为依赖里有几个“巨兽”：OpenCASCADE、VTK、ITK、Boost、Python。

看一个项目的构建系统，重点看三件事。

**依赖怎么来。** `find_package` 要求用户预装，`FetchContent` 会自动下载，vcpkg/Conan 管版本，子模块把源码放进仓库。四种方式对应四种用户群：前者适合发行版，后者适合开发者。

**Qt 版本策略。** Qt 5.15 是 LTS，Qt 6 是现在。同时支持两个大版本意味着大量条件编译，很多项目在 2024 年前后完成了迁移，也有的干脆只支持 Qt 6。这直接影响你能不能把它嵌进现有产品。

**分发形态。** Windows 上 `windeployqt` 收集 DLL，Linux 上 AppImage 或 Flatpak，macOS 上 `.app` 加签名公证。别小看这一步，工业软件的客户常常在内网，安装包能不能离线装，决定了它能不能进现场。

## 2.6 一张检查表

把上面的观察压成一张表，去任何一个仓库都能用。

| 观察点 | 看哪里 | 判断标准 | 对你的意义 |
| --- | --- | --- | --- |
| 分层 | 顶层目录、CMake 目标 | core 是否依赖 gui | 能不能只复用内核 |
| 数据模型 | `Document` / `Scene` / `Project` 类 | 有无稳定 ID、显式依赖、版本化序列化 | 能不能长期演进 |
| 交互 | `undo`、`command`、`tool` 关键字 | 是否所有修改都走命令 | 撤销是否可信 |
| 扩展 | `plugin`、`python`、`script` 目录 | 脚本能否写模型 | 二次开发成本 |
| 构建 | `CMakeLists.txt`、CI 配置 | 依赖来源与 Qt 版本 | 集成难度 |
| 许可 | `LICENSE`、文件头 | 是否 LGPL/ GPL/ 双许可 | 商业可行性 |

## 2.7 读代码的顺序

拿到一个新项目，我通常这样走一遍，两三个小时能建立整体印象。

1. 从 `main()` 开始，看它创建了哪些顶层对象，顺序是什么。
2. 找到文档类，读它的成员和序列化函数。
3. 找到命令基类，读两个具体命令。
4. 找到插件注册处，读一个最小的插件。
5. 找一个完整用例：打开文件 → 选中 → 修改 → 保存，跟一遍调用链。

不要从工具类开始读，也不要一上来就看渲染。渲染是结果，前面四步才是原因。
